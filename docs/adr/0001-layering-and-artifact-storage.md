# 0001 分层与产物存储边界

日期：2026-09-20
状态：已接受

## 背景

要把 Modal 上的能力（先 Qwen-Image 生图，后续视频、LLM）封装成个人软件。问题是：一开始就做"一站式平台"，还是按需做。

参考实现见 agent-media-lab 的 `tools/gpu/`。那边同一套"plan → 派发 → worker.execute() → Volume → 下载回本地"已经复制了三份（音频 GPU、Qwen-Image、VLM），`image_jobs.py` 与 `modal_jobs.py` 之间已有四百多行差异——分叉已经在发生，不是将要发生。

## 决策

分三层，各自的时机不同：

1. **执行层（Modal 抽象）**：现在就抽，但只抽最薄的一层——任务提交、状态、超时、重试、定价标签、产物清单。不抽统一网关、统一 UI、插件系统。
2. **产物层（存储）**：现在就定死。对象存储 + 元数据表；Modal Volume 退回只做模型缓存。
3. **产品层**：按需。一个能力一个纵向切片，跑通一个再加下一个。

## 理由

- **产物层是唯一"做错要拆房子"的部分。** Volume 没有对外 URL、没有权限模型、并发读延迟差。不换掉它，图床、分享链接、多端访问都要重做；而现在换的成本最低。
- **产品层的接口应由第二、第三个能力倒逼出来。** 现在只有一个能力，做出来的抽象就是 Qwen-Image 的形状；视频（长任务、进度回调、大文件）和 LLM（流式、按 token 计费、密钥轮换）会把它撞坏。
- **冷启动决定产品形态，而这只能实测得到。** 在 `min_containers=0`、`scaledown_window=2` 下首次加载是分钟级，产品天然是排队式异步；换成保温容器则是另一套成本结构。在拿到实测数据前无法为它设计平台。
- **统一镜像的教训已有先例**：agent-media-lab 最终按依赖隔离出三个镜像。

## 判断规则

抽象"与模型无关、且已经复制 ≥2 次"的东西；"与模型相关或只有 1 个用例"的东西保持分叉。

## 后果

- aladin 的第一个交付物是一个能端到端跑通的图片切片，不是一个平台。
- 平台化（统一 UI / 网关 / 多能力编排）推迟到第二个能力落地后重新评估。
- LLM API 管理独立立项，不并入本平台。
